## 6. REMEDIATION PLAN  

### Issue 1 – SSH brute‑force on `root`  
| Step | Action |
|------|--------|
| **Immediate** | **Lock down `root` login**: `PermitRootLogin no` in `/etc/ssh/sshd_config`; reload `sshd`. |
| **Short‑term** | Deploy **fail2ban** or **SSHGuard** with a rule to ban IPs after 3 failed attempts. |
| **Long‑term** | Enforce **key‑based authentication only**; disable password auth (`PasswordAuthentication no`). Rotate any existing root keys. |
| **Code/Config** | ```bash\n# /etc/ssh/sshd_config\nPermitRootLogin no\nPasswordAuthentication no\n``` |
| **Monitoring** | Alert on **`sshd` failed password** > 5 per 5 min, and on **new IPs** hitting port 22. |

### Issue 2 – UDP flood (port 2055)  
| Step | Action |
|------|--------|
| **Immediate** | Verify if the server *should* listen on UDP 2055. If not, **drop** traffic at the firewall (`ufw deny in to any port 2055`). |
| **Short‑term** | Add a **rate‑limit** rule: `ufw limit proto udp from 197.248.225.61 to any port 2055`. |
| **Long‑term** | Identify the source (owner of `197.248.225.61`). If malicious, **report to upstream provider** and consider **black‑hole routing** or **BGP filtering**. |
| **Code/Config** | ```bash\nufw deny in proto udp to any port 2055\n# optional rate‑limit\nufw limit proto udp from 197.248.225.61 to any port 2055\n``` |
| **Monitoring** | - Netflow / sFlow to detect spikes on UDP 2055.<br>- Alert on **`kernel: [UFW BLOCK]`** count > 10 per minute for the same source. |

### Issue 3 – SignalR/WebSocket 502 errors  
| Step | Action |
|------|--------|
| **Immediate** | Check **upstream proxy / load balancer** (NGINX, HAProxy, Azure Front Door, etc.) for mis‑configuration that returns 502 on the `/hub` endpoint. Restart the proxy service. |
| **Short‑term** | Enable **detailed proxy logs** (e.g., `error_log` at `info` level) to capture why 502 is returned. |
| **Long‑term** | Implement **health checks** on the SignalR service; configure the proxy to route only to healthy back‑ends. Consider adding **circuit‑breaker** logic in the client. |
| **Code/Config** | Example NGINX fix: ```nginx\nlocation /signalr {\n    proxy_pass http://localhost:5000;\n    proxy_http_version 1.1;\n    proxy_set_header Upgrade $http_upgrade;\n    proxy_set_header Connection \"Upgrade\";\n    proxy_read_timeout 60s;\n}\n``` |
| **Monitoring** | - Alert on **HTTP 502** responses from the proxy for `/hub` > 5 per minute.<br>- Alert on **SignalR client reconnection attempts** > 3 within 1 min. |

## 7. PREVENTIVE MEASURES  

1. **Zero‑trust SSH**  
   - Disable password auth globally; enforce MFA for privileged accounts.  
   - Deploy **jump host / bastion** with MFA and IP allow‑list.  

2. **Network hardening**  
   - Maintain an **ingress ACL** that denies any traffic to unused ports (e.g., UDP 2055).  
   - Enable **connection tracking** limits (`conntrack -C`) to guard against flood attacks.  

3. **Observability uplift**  
   - Collect **full packet capture** (or at least flow logs) for the offending source IP to aid forensic analysis.  
   - Centralize **UFW kernel messages** into a SIEM with threshold alerts.  

4. **Application resiliency**  
   - Add **automatic retry with jitter** in SignalR clients; expose reconnection metrics to monitoring.  
   - Use **helm / Docker health‑checks** to restart the SignalR service automatically if it becomes unhealthy.  

5. **Regular security audits**  
   - Run **`ssh-audit`** and **`nmap`** scans quarterly.  
   - Verify that **root login** is disabled on all production nodes.
