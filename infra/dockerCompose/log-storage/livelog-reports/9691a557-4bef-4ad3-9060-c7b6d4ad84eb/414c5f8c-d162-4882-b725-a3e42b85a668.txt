## 6. REMEDIATION PLAN  

### Issue 1 – `/.env` exposure
- **Immediate:** Remove or relocate the `.env` file outside the document root. If it must stay, add a web‑server rule (`Django/Flask/Apache/Nginx`) to **deny all** requests to `/.env` (`return 403;` or `RewriteRule "^\.env$" - [F]`).
- **Short‑term:** Invalidate any credentials that may have been leaked (DB passwords, API keys, JWT secrets). Rotate them.
- **Long‑term:** Adopt a **configuration‑as‑code** approach (e.g., Docker secrets, Vault) so that secrets are never stored in plaintext files served by the web server.
- **Code/Config:**  
  ```nginx
  location ~* \.env {
      deny all;
      access_log off;
  }
  ```
- **Monitoring:** Alert on any HTTP 200 response for `/.env` or `/.git/*`. Use a WAF rule to block such URIs.

### Issue 2 – `/.git/config` exposure
- **Immediate:** Move the `.git` directory outside the web root or add a deny rule similar to above (`location ~ /\.git { deny all; }`).
- **Short‑term:** Audit the repository for any sensitive data that might have been exposed and purge it.
- **Long‑term:** Use **Git shallow clones** or `git archive` deployments that do not include the `.git` folder on production.
- **Monitoring:** Same as above – alert on 200 responses for `/.git/*`.

### Issue 3 – PHPUnit files visible / present
- **Immediate:** Verify that no vendor directories (especially `vendor/phpunit/`) exist on production. If they do, delete them.
- **Short‑term:** Add a rule to return 404 for any `*/phpunit/*` paths.
- **Long‑term:** Enforce **build‑pipeline hygiene**: only copy compiled/artifact files to production; never ship dev dependencies.
- **Monitoring:** WAF signatures for known PHPUnit exploit paths.

### Issue 4 – WordPress directories publicly readable
- **Immediate:** If WordPress is not in use, remove it. If it is, ensure **index.php** protection, disable directory listing, and apply the latest security patches.
- **Short‑term:** Add `Options -Indexes` (Apache) / `autoindex off;` (Nginx) and restrict access to admin paths (`/wp-admin/`) to trusted IPs.
- **Long‑term:** Deploy a **Web Application Firewall** (e.g., ModSecurity, Cloudflare) with WordPress rule‑sets.
- **Monitoring:** Alert on HTTP 200 for `/wp-admin/`, `/wp-includes/`, `/xmlrpc.php` from unknown IPs.

### Issue 5 – OpenWRT `/cgi-bin/luci` probe
- **Immediate:** Verify that this endpoint is not intended to be exposed. If it belongs to an internal router, adjust DNS/reverse‑proxy so it does not resolve to the web server’s IP.
- **Short‑term:** Block the path via a 403 rule.
- **Long‑term:** Network segmentation – ensure internal device management interfaces are on isolated subnets not reachable from the internet.
- **Monitoring:** Alert on any request matching `/cgi-bin/luci*`.

## 7. PREVENTIVE MEASURES  

1. **Hardening baseline** – Deploy a standard hardening checklist (disable directory listing, block hidden files, restrict admin URLs).
2. **Static file whitelist** – Serve only explicitly allowed static assets (e.g., `*.css, *.js, *.png, *.jpg`) and deny everything else.
3. **Continuous deployment validation** – Include a **post‑deployment scan** (e.g., `nikto`, `trivy`) that checks for accidental exposure of sensitive files.
4. **Secrets management** – Move all configuration secrets to an external vault; never check them into the repo or copy them onto the web root.
5. **Web‑Application Firewall** – Enable a WAF with rule‑sets for common scanners (PHPUnit, WordPress, CVE‑specific patterns).
6. **Logging enrichment** – Add request‑duration and upstream latency fields to the access log for performance monitoring.
7. **Alerting matrix** – Create alerts for:
   - HTTP 200 on `/.env`, `/.git/*`, `/.ht*`, `/.env.*`
   - 4xx spikes for known exploit paths (PHPUnit, WordPress, Cisco, OpenWRT)
   - Sudden increase in 404/400 ratio (> 30 % over a 5‑minute window)
