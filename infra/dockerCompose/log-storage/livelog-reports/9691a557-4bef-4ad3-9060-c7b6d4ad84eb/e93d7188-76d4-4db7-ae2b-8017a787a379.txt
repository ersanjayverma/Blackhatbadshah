## 6. REMEDIATION PLAN  

### Issue 1 – SignalR/WebSocket 502 Failures  

| Stage | Action |
|-------|--------|
| **Immediate** | 1. Verify the health of the remote SignalR hub (check its logs, service status, and any recent deployments).  <br>2. Confirm network reachability from `vmi3002731` (run `curl -v https://<hub‑host>/hub` or `telnet <hub‑host> 443`). |
| **Short‑term** | 1. Increase the worker’s retry back‑off (e.g., exponential back‑off up to 30 s) to reduce rapid reconnection storms. <br>2. Temporarily enable **keep‑alive** on the underlying HTTP client to detect broken connections earlier. |
| **Long‑term** | 1. Fix the root cause on the hub side (e.g., reload reverse‑proxy, scale out, patch bug causing 502). <br>2. Deploy a **circuit‑breaker** in the worker to pause attempts after N consecutive failures and raise an alert. |
| **Code/Config** | - In the worker’s SignalR client configuration, set `ServerTimeout`, `HandshakeTimeout`, and `KeepAliveInterval` to values > 30 s. <br>- Add health‑check endpoint on the hub and monitor it via Prometheus/Alertmanager. |
| **Monitoring** | - Alert on **HTTP 502** or **WebSocket close** events from the worker (count > 5 per 5 min). <br>- Create a Grafana panel showing *SignalR connection status* over time. <br>- Track firewall drop‑rate for UDP 2055 to spot spikes. |

### Issue 2 – UDP 2055 Flood / Block  

| Stage | Action |
|-------|--------|
| **Immediate** | 1. Verify if the host *should* listen on UDP 2055 (NetFlow collector, sFlow, etc.). If **yes**, adjust UFW to **allow** traffic from the legitimate exporter IP(s). <br>2. If **no**, add a **rate‑limit** rule to drop after a threshold (e.g., `ufw limit 2055/udp`). |
| **Short‑term** | 1. Add a **log‑only** rule preceding the block to capture a few samples and identify the legitimate source (if any). <br>2. Block the offending IP (`197.248.225.61`) at the perimeter firewall if it is malicious. |
| **Long‑term** | 1. Deploy **fail2ban** or similar to automatically ban IPs that generate > X UDP packets per minute. <br>2. Harden the NetFlow collector configuration (if used) to bind to a specific interface and restrict source IPs. |
| **Code/Config** | - `ufw allow from <trusted‑netflow‑src> to any port 2055 proto udp` (if needed). <br>- `ufw deny in from 197.248.225.61` to stop the flood. |
| **Monitoring** | - Create a metric `ufw_dropped_udp_2055_total` and an alert if it exceeds a configured baseline (e.g., > 1000 drops per hour). <br>- Log aggregation (e.g., Loki) to visualize the drop pattern and correlate with upstream NetFlow exporter health. |

## 7. PREVENTIVE MEASURES  

1. **Centralised Logging & Rate‑Limiting** – funnel kernel UFW messages to a log aggregation platform and enable automated throttling (fail2ban) for repetitive source IPs.  
2. **Network‑Path Health Checks** – schedule periodic `ping`/`tcping` to the SignalR hub and upstream NetFlow exporters; raise alerts on latency spikes or packet loss.  
3. **Service‑Level SLAs** – define a Service Level Indicator (SLI) for “SignalR connection uptime %” and an associated SLO; drive alerting on breach.  
4. **Configuration Audits** – regularly review firewall rules to ensure they match the intended traffic matrix (e.g., NetFlow, monitoring, API).  
5. **Chaos‑Testing** – periodically simulate network failures (e.g., drop DNS, block hub port) to verify the worker’s reconnection/back‑off logic and the alerting pipeline.
